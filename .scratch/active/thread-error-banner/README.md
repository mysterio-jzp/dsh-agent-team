## 对照实验（2026-10-20，三棵树，同一用例、同一组操作）

同一 `node_modules`、同一 `npm run build`、同一浏览器、同一组操作步骤，**只有树不同**：

| 树 | 是什么 | `offset` | 行序号 | `emptyFrames` | `mounts` | 结果 |
|---|---|---|---|---|---|---|
| `3c81188` | 两笔读者位置修复之前 | **71 → 210** | 3/15 → 3/15 | 7 | 0 | **红**（`expected 210 to be 71`） |
| `09d6e07` | 两笔修复之后（`a61f4aab` 的父） | 71 → 71 | 3/15 → 3/15 | 7 | 0 | 绿 |
| `a61f4aab` | 本笔叠在其上 | 71 → 71 | 3/15 → 3/15 | 7 | 0 | 绿 |

**读法：**

1. **红读数只存在于 `3c81188`**：139 像素位移，读者那一行被推下屏幕，与最初报的现象吻合。修好它的是 `3c81188`（`fix: return the thread view to the reader's last position`）与 `09d6e07`（`fix: restore the reader's place when the thread view returns`）。**本笔对此贡献为零**。
2. **`mounts` 三棵树都是 0** ⇒ 这条读数证明「没有整块重挂」，但无法把本笔与「位置补偿」区分开。
3. **`emptyFrames` 三棵树都是 7** ⇒ 按归因三选一，属**既有缺陷**：本笔既不引入也不修。
4. **教训**：判「某现象已修」必须先在**一棵红的树**上量出红读数；「上一个提交」不等于「上一个绿点」——本次被指定的对照树 `09d6e07` 本身已经是绿的，必须再往前探一棵才找到红点。判据若不含这一步，检验性会退回「看起来对」。

三棵树上的执行方式：在共享检出上只把 `TeamThreadPage.tsx`、`timeline-scroll.ts` 两个源文件切到目标树，跑完 `git checkout HEAD --` 还原，并用 `diff -q` 对备份逐字节确认、重跑确认恢复后仍为绿。（评审意见：更稳妥的做法是独立工作树加符号链接依赖；本次为避开「两份 `node_modules`」这个新变量而没有那样做。）

读数口径：
- `mounts`：整数，对话行被插入文档的次数（`MutationObserver`）。
- `emptyFrames`：整数，`requestAnimationFrame` 里「Thread 页存在但一行对话都没有」的帧数。
- `offset`：有符号 CSS 像素，所读行的 `top` 减滚动容器的 `top`。

用例位置：`scripts/team-ui.e2e.ts` 的 `keeps the fact under the reader still and never remounts the conversation across a runtime error` 与 `keeps the reading place when the discussion returns from the Human to-do board`。

## 必须随交付说明保留的更正

1. **最初判断「对话区没有被重建」、随后判断「横幅插在时间线上方把内容推下去」，两条都被浏览器读数推翻。** 实测 `bannerInsideBox = false`：风险横幅在 `surfaceHeader` 内，滚动容器是 header 的兄弟节点；横幅出现不改变容器的 `scrollHeight`，改的是容器自身在页面上的位置。
2. **导出的 `compensateGrowth` 无调用点，`fc52cce` 删除，行为不变**（删的是别名与接口承诺，`compare` 与 hook 内部的 `measureGrowth` 都在）。真正在跑的是 hook 内部的自动高度补偿：对**容器内**增高有效，对**横幅**（容器外、不改 `scrollHeight`）无效。代码里那段原称「处理横幅」的注释与事实相反，同笔改掉；**改后的注释明确禁止用 `scrollTop` 补偿横幅，并说明损失发生在盒子之上**——下一个人遇到横幅推走行时，需要的是「别这么补」，而不是「注释改过了」。
3. **「闪」未复现。** 把 `TeamThreadPage.tsx` 的改动撤掉后重跑同一用例同样通过，说明该用例对此没有分辨力；正反两个方向都不能拿它当证据，它的定位只是防退化守卫。
4. **`6052511` 的复位收窄：消除一条结构性缺陷，无现象读数。** 一个只该在换线程时清空的状态被写成每次重跑都清空，本身就是缺陷；没有读数证明它对应任何已复现现象（@代码审核 判定保留）。
5. **`offset` 71 → 71 的适用范围**：只证明「切待办往返后所读行仍在原处 / 现在没落回最早」。**不能**据此说 Human 当时的现象就是这个——若真落回最早，所读行会在屏幕外，`offset` 会是很大的值。
